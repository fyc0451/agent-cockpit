# Agent Cockpit · 个人/团队双模式设计

> 状态：v3 已确认
> 关联实现细节：`agent-chat/DESIGN.md`（共享 hub / 公共频道 / 身份目录 / 在线状态的技术设计）

## 1. 产品定位

Agent Cockpit 定位为**"跑在浏览器里的编码 agent 驾驶舱"**，从单机工具演进为**个人与团队皆宜**的应用：

- **个人模式（现状）**：单机部署，看自己的 agent、接管终端、收发自己的消息——零团队概念，不引入任何额外复杂度。
- **团队模式（扩展）**：多人、多机。各机仍用自己的 cockpit 界面，但跨机沟通走独立服务器上的团队共享 Hub；服务器提供**逻辑项目群组 + 身份目录 + 在线状态 + Web 看板**，便于 @ 协作者。
- **核心原则**：本机工作区负责运行和终端，远程 Hub 负责团队身份与通信。两者通过显式操作关联，不共享数据库，也不按本机路径自动映射项目。

## 2. 模式模型

| 维度 | 个人模式 | 团队模式 |
|---|---|---|
| 消息服务 | 本机 Agent Mail（技术项目可使用目录键） | 独立机器上的团队 Hub（逻辑群组无目录键） |
| 身份注册 | 本机 `am-register` | 注册到远程 Hub `agents` 表（花名全局唯一） |
| 公共频道 | 不启用 | 启用（按项目） |
| 身份目录/在线 | 不需要 | 需要（@ 用） |
| Web 看板 | 不需要 | 需要（频道消息流/成员） |
| 消息回执 | 本机 DB（claim/complete 权威） | 服务器仅持久投递（@ 收件箱/频道历史），认领仍在本地 sidecar |

团队模式由 Cockpit 配置远程 Hub 的 HTTPS 地址与认证信息开启。本机 Agent Mail 项目不会迁移、同步或显示为团队群组。

### 逻辑群组模型

```
TeamProject（用户注册、首次为空、slug 全局唯一）
    └── routing Project（Hub 内部生成 team:<uuid>，仅用于消息与 Agent 路由）
```

- `TeamProject` 是用户界面唯一可见的“项目/群组”，由管理员在 Hub 上注册；新 Hub 的群组列表默认为空。
- 现有 Agent Mail `Project` 是技术路由记录，可能含客户端工作区键；Team API 永不枚举或接管这些记录。
- Hub 不接收客户端文件路径，不读取 Herdr、worktree 或本地任务。工作区 Agent 加入群组必须经过后续的显式绑定流程。

### 部署拓扑

```
① 纯个人：本机 Cockpit + 本机 Agent Mail，无团队群组组件。
② 团队 + 各机 cockpit：每机 cockpit 界面照旧；mail 通信指向团队服务器共享 hub；
   服务器另跑 Web 看板。
③ 服务器集中驾驶舱（可选）：cockpit 直接部署在服务器，人用浏览器登录操作
   （现有局域网/手机访问已支持），各机 agent 仍是本地进程，只是看板集中。
```

## 3. 能力地图（已有 → 团队增强）

| 能力 | 个人现状 | 团队增强 |
|---|---|---|
| 看板 | 本机 herdr session 状态 | 保持本机视图；可选聚合团队各机 run 汇总（M5 可选） |
| 真终端 | 本机 PTY 接管 | 不变（不做跨机终端接管，保持简单） |
| 消息 | 本机 Agent Mail 单聊 | 共享 hub；按项目公共频道；`@花名` 跨机；在线状态 |
| 待办 Inbox | 本机 blocked/失败/待审 | 频道 @ 提及可汇入待办（可选） |
| 文件/代码 | 本机白名单沙箱 | 不变（团队共享文件属后续范围） |
| 截图→agent | 本机上传转 `@/path` | 不变 |
| 推送 | 本机 Web Push | 不变 |

**团队化只动"消息与身份"一层**，其余能力保持单机语义，避免 scope 膨胀。

## 4. 团队通信层（核心）

详见 `agent-chat/DESIGN.md`（方案 Y），要点：

- **Hub 保持哑总线；协调权威留在本机 sidecar**（claim/complete/checkpoint 状态机不迁移，保住刚落地的可靠消费语义）；服务器只扩展"频道 fanout + 身份目录 + 在线 + @ 持久投递"；
- 每项目一个公共频道 `channel:<项目slug>`；agent 默认归属注册项目，可额外订阅其他项目；
- **@ 定向消息 = durable 收件箱**（服务器持久队列，离线积压、上线补收），与频道读位解耦，跨项目 @ 天然可达；
- 频道消息 = 持久历史 + per-agent 读游标（提及 + 自游标未读，不做全量流）；
- 身份目录 = Hub `agents` 表（花名/program/所属项目/注册时间）；
- 在线 = **被动心跳**（mail 工具打点 `last_active_ts`，阈值对 poll 间隔校准），绝不反向唤醒 agent；
- Web 看板：频道消息流、发言框 `@` 自动补全（在线优先）、成员栏绿/灰点；人 = `human:<昵称>`。

## 5. 身份与安全

- **个人**：本地 registry JSON、本机 Agent Mail 与 coordination.sqlite3 是权威，团队组件不启动。
- **团队**：服务器 Hub `agents` 表 = 通讯录；花名全局唯一（统一服务器注册 + 冲突检测，存量按物理 agent 迁移）；人 = `human:<昵称>`（登录态绑定）。
- **账号**：系统管理员生成一次性邀请码；成员注册后为 pending，需系统管理员批准。批准账号不会自动加入任何群组；停用后 Cockpit 在每次 Team API 代理前向 issuer 复核状态。
- **登录态**：Human JWT 只进入 Cockpit 的 `HttpOnly + SameSite=Strict` Cookie，页面脚本和 `sessionStorage/localStorage` 都不读取或保存 JWT、密码。
- **群组**：只在远程 Hub 注册；不从 Cockpit 所在机器发现目录或工作区。群组与本机 Agent 的关系只能显式建立和撤销。
- **送达 vs 认领**：送达（durable 收件箱/频道历史）在服务器；认领/完成（处理状态）在本地 sidecar——解耦，不产生双重 claim 权威。
- **token**：服务器持有并校验（共享或 per-agent）token，但**不存 agent 私钥/凭据**；beta 建议直接用 per-agent token（支持归因/吊销）。
- **sender/human 可信边界**：共享 token 下 sender 是断言值，beta 以"内网内断言即信任"为已知边界；per-agent token 落地后按 token 归属绑定 sender；`human:` 的 stop/redirect 能力必须绑定登录态，不得凭共享 token 冒认。
- 多团队 RBAC / 审计（扩展现有 Hub 审计日志）/ 消息隔离 = **beta 后**。
- **共享 Hub 是不可信数据源，不是控制面**：消息正文、主题、sender、intent 与 Hub 返回的 delivery 元数据只可读取/展示；不得据此执行 shell、写文件、调用任意工具、切换任务或向 Herdr pane 注入提示。
- Web 端对 Hub 文本统一转义；后端只调用代码中固定列出的 MCP 工具，不接受 Hub 返回的工具名。`@` 只生成持久消息/待处理提示，不等于授权执行。
- 只有用户在 Cockpit 内作出的显式操作可以进入本地受控流程。为兼容个人模式，只有 loopback Hub 可以复用现有本地 coordination→pane 通知；共享/远程 Hub 的响应不会创建本地 receipt、checkpoint 或终端通知。

## 6. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | 个人模式回归 | 现有功能全量测试通过；未配置远程团队 Hub 时，本地 coordination sidecar 单机工作不变 |
| M1a | Hub 内网可达 + 跨机 send/fetch/ack | 两机 agent 跨机基础通信全链路成功 |
| M1b | Hub 扩展（频道/目录/@ durable 收件箱/per-agent token/审计） | 服务器扩展可用；协调测试移植/扩展到服务器投递路径有回归保护 |
| M2 | 同项目公共频道 + 读游标 + @ durable 投递 | 同项目 agent 跨机频道发言/收听/离线补收成功 |
| M3 | 身份目录 + 在线 + Web 看板 + 跨项目 @ | 目录/在线可见、跨项目 @ 可达、人+agent 同场看板 |
| M4 | 团队试点 | 真实 codex-main ↔ opencode-main（+1 台外部机）跨机互 @ 闭环 |
| M5 | per-agent token 收尾 / 待办汇入频道提及 | 试点后按真实协作痛点决定 |

- 协调权威留本地，M1b 不迁移存量在途消息；团队试点以新项目/新频道起步（dual-run 故事），存量数据迁移试点后再定。
- run 跨机聚合推迟到"编辑任务说明+持久化"落地之后，避免 garbage-in/garbage-out。

## 7. 设计原则（评审用）

1. **个人不背团队成本**：团队能力全部落在服务器侧，单机安装不启动任何新组件。
2. **通信层可降级**：hub/频道/看板挂掉，看板、终端、文件、待办、推送照常（沿用现有"Agent Mail 可选"的降级哲学）。
3. **agent 的 CLI 调用不变**：所有团队能力由 cockpit/服务器端承担，各 agent 只依赖 mail-send/mail-recv（CLI 原样，非"零改造"表述）。
4. **协调权威不迁移**：claim/complete/checkpoint 状态机留在本机 sidecar，不在外部 Hub 内重建，可靠性保证不丢失。
5. **最小可用先行**：M1a→M4 每步都可独立验收，不搞一次性大重构。

## 8. 待确认开放点

1. 团队模式启动入口已定为 Cockpit 设置页配置远程 Hub；生产地址必须使用 HTTPS，不把密码或 token 持久化到页面代码；
2. 服务器 Web 看板独立服务还是挂在 cockpit 下（建议独立轻量服务，避免动主链路）；
3. per-agent token 生成/下发流程（beta 可先共享 token 过渡）；
4. 存量身份花名唯一化的迁移节奏与范围；本机技术项目明确不迁移为群组；
5. M5 三项哪些值得做，试点后按真实协作痛点决定。
